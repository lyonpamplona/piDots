PASSO 01

Contexto & Genealogia: Da Nuvem Proprietária ao Edge Soberano

Em 29 de setembro de 2026, a OpenAI introduziu o conceito de Dots — agentes inteligentes de inteligência artificial que atuam como colegas de trabalho perenes (always-on AI coworkers), equipados com sistemas de arquivos próprios, capacidade de executar tarefas em computadores e reter histórico prolongado de trabalho entre múltiplos canais (Web, Voz, Slack).

A comunidade de código aberto respondeu imediatamente com implementações autônomas para evitar o aprisionamento tecnológico (*vendor lock-in*). A principal referência consolidada é o CopilotKit/OpenDots, que padronizou a interação humano-agente por meio do AG-UI Protocol (Agent-User Interaction Protocol).

OpenAI Dots
Proprietário
Infraestrutura fechada em nuvem, custo por minuto de execução, dependência total de fornecedor externo.
CopilotKit / OpenDots
Open Source
Padrão da comunidade, protocolo AG-UI, contêineres Docker pesados, projetado para servidores com 16GB+ RAM.
piDots (Nossa Solução)
Edge-Native
Monólito modular em Python assíncrono, SQLite WAL, consumo de memória < 300MB, 100% calibrado para Pi 4B.

PASSO 03

Diagnóstico de Restrições Críticas no Hardware do Raspberry Pi 4B

O Raspberry Pi 4B (4GB) é uma máquina extraordinária para computação de borda, porém opera com restrições arquiteturais que punem implementações de software concebidas para nuvem comercial:

Componente do Pi 4B Especificação Limite Comportamento com OpenDots Original Estratégia de Correção no piDots
CPU Cortex-A72 (Quad-Core) 1.5 GHz, sem aceleração FP16, NEON 128-bit Chromium e Node disparam 100% de uso contínuo, causando throttling térmico a 80°C Single-worker assíncrono em Python com uvloop e limitação cgroups v2 (CPUQuota=50%)
Memória RAM (4GB LPDDR4) Largura de banda de ~4.5 GB/s compartilhada com GPU Saturação acima de 2.5GB elimina o page cache do kernel, causando travamento geral Teto rígido de 250MB para a stack inteira; caches de banco em 16MB
Armazenamento Flash (MicroSD) Barramento SDR104, escritas aleatórias lentas (1.000 IOPS) Fsync constante de logs e SQLite destrói as células NAND do cartão em semanas SQLite em modo WAL com synchronous=NORMAL, logs em tmpfs e debouncing de escritas
Comportamento Térmico Dissipação passiva atinge 80°C em 3 minutos sob carga Queda de clock de 1.5 GHz para 600 MHz; latências de resposta aumentam 300% Refrigeração ativa recomendada + algoritmo de Thermal Backoff lendo a temperatura do SoC

PASSO 05

Estratégia de Inteligência: Gateway OpenAI-Compatível com Resiliência a 503

Conforme as diretrizes inegociáveis do usuário, o provedor e modelo mantêm-se exatamente como configurados: Universal Gateway qwen3.8-27b. Esta decisão é tecnicamente perfeita para o Raspberry Pi 4B por três motivos:

Capacidade Cognitiva
27B Parâmetros
Capacidade de raciocínio, estruturação JSON e autocorreção infinitamente superior a SLMs locais de 1.5B/3B.
Preservação de RAM
Zero Carga Local
Economia de 2.2GB de RAM no Pi 4B, evitando a sobrecarga de carregar pesos densos na SDRAM unificada.
Segurança Térmica
< 50°C no SoC
O processador ARM Cortex-A72 atua apenas como cliente HTTP assíncrono, operando frio e responsivo 24/7.
Blindagem Contra Erros HTTP 503 (Circuit Breaker com Jitter)
Mesmo diante de indisponibilidades esporádicas (HTTP 503) do provedor remoto, o piDots implementa um algoritmo de backoff exponencial com jitter aleatório (1.5s, 3.5s e 7.0s). Isso retém a thread e o contexto do agente sem quebrar o fluxo de trabalho do usuário ou resetar o estado da conversa.

PASSO 07

Proteção Crítica da Mídia Flash (Prevenção de Queima do MicroSD)

O calcanhar de Aquiles histórico do Raspberry Pi é a queima do cartão MicroSD decorrente da amplificação de escrita (*write amplification*) gerada por commits frequentes de banco de dados e logs descontrolados. O piDots implementa um protocolo inegociável de proteção flash:

SQLite WAL com synchronous=NORMAL
Elimina o bloqueio e fsync a cada transação individual; escritas ocorrem sequencialmente em append-only sem risco de corrupção.
Debouncing de Estado em RAM (Buffer de 120s)
O raciocínio intermediário dos Dots reside exclusivamente em memória RAM. A gravação em disco ocorre apenas na conclusão de tarefas ou a cada 120 segundos em lote.
Diretórios Temporários e Logs em tmpfs
O diretório /tmp e logs voláteis do systemd são alocados diretamente na memória RAM, poupando as células NAND do cartão.
Rotação Rígida de Logs Docker
Todo container deve possuir rotação de logs mandatória configurada para max-size: 5m e max-file: 2.
PASSO 08

Isolamento Seguro via Bubblewrap (bwrap) Sem Docker Overhead

No OpenDots original, cada Dot exige um container Docker individual com overhead de ~150MB e latência de subida de mais de 1 segundo. No piDots, a execução segura de scripts shell adota o Bubblewrap (`bwrap`) nativo do Linux: 

# Invocação ultraleve da sandbox Bubblewrap no piDots
bwrap \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /bin /bin \
  --tmpfs /tmp \
  --bind /mnt/storage/piDots/workspaces/dot_default /workspace \
  --chdir /workspace \
  --unshare-pid \
  --unshare-net \
  bash -c "python3 script_gerado.py"
Tempo de Inicialização
< 15 milissegundos
100 vezes mais rápido que o Docker run tradicional, ideal para turnos rápidos de execução.
Consumo de Memória
< 3 MB de RAM
Reutiliza as bibliotecas e o kernel do host sem criar interfaces de rede virtuais desnecessárias.
Segurança de Sandbox
Namespaces Linux
Sistema de arquivos montado como somente-leitura; escrita autorizada estritamente na pasta do Dot.

Navegação Web em Duas Camadas: Fim do Chromium Contínuo

Manter um navegador Chromium com interface gráfica emulado rodando em background no Raspberry Pi 4B é a principal causa de travamento do OpenDots padrão. O piDots introduz o modelo de Navegação Web em Duas Camadas:

Camada de Navegação Mecanismo Técnico Casos de Uso Consumo & Tempo
Tier 1: Extração Semântica (95% dos casos) HTTPX assíncrono + Trafilatura Markdown Extractor Leitura de documentações, artigos técnicos, repositórios GitHub, blogs e páginas informativas 18 MB RAM | ~200 ms
Tier 2: Headless Efêmero (5% dos casos) Chromium headless efêmero com flags severas (--single-process, --disable-gpu) Páginas com renderização obrigatória de Single Page Apps (SPA) ou autenticação via formulário ~180 MB RAM | Encerramento após 60s
PASSO 10

Governança Rigorosa e Human-in-the-Loop (HITL)

Agentes totalmente autônomos que executam comandos shell sem supervisão representam alto risco operacional. O piDots implementa governança Deny-by-Default com pontos de checagem obrigatórios:

Gatilhos de Congelamento e Aprovação Humana
A execução é pausada imediatamente e emite um evento hitl:approval_required na interface web sempre que o agente tentar:
  • Executar comandos de escrita no terminal com flags destrutivas (ex: remoção recursiva, alteração de permissões).
  • Modificar arquivos de configuração fora do workspace designado.
  • Acessar endpoints externos não declarados na lista segura de domínios permitidos.
  • Criar ou registrar novas habilidades (skills) no sistema.

Roadmap Técnico de Implementação Passo a Passo (Checkpoints)

Planejamento faseado para o desenvolvimento do projeto piDots em /mnt/storage/piDots, com checkpoints auditáveis antes de cada transição:

Fase 1: Setup da Base e Storage SQLite WAL
Estruturação do repositório em /mnt/storage/piDots, configuração do ambiente Python 3.13, criação do esquema de banco SQLite WAL com pragmas calibrados e migrações iniciais.
Fase 2: Cliente AI Gateway Resiliente e Loop Assíncrono
Implementação do cliente HTTP assíncrono com circuit breaker e backoff exponencial com jitter para o modelo qwen3.8-27b, e máquina de estados da thread com teto de iterações.
Fase 3: Sandboxes Bubblewrap e Ferramentas Leves
Construção do executor seguro via Bubblewrap para shell isolado, scraper semântico Trafilatura e gerenciador de arquivos seguro com leitura/escrita atômica.
Fase 4: Frontend PWA Estilo IDE e Streaming SSE
Interface web dark mode minimalista com Server-Sent Events (SSE), buffer circular de 150 nós no DOM, cartões interativos de aprovação HITL e fontes locais WOFF2.
Fase 5: Testes de Carga, Auditoria e Empacotamento Docker Edge
Validação contínua sob estresse no Raspberry Pi 4B, medição de temperatura do SoC (< 70°C), confirmação de consumo < 250MB RAM e geração de compose final com rotação de logs.
